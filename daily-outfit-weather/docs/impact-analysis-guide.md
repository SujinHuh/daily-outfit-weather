# 범용 사전 영향도 분석(Pre-Implementation Impact Analysis) 표준 지침서

이 문서는 **Daily Outfit Weather** 프로젝트에서 **새로운 기능을 개발하기 '전'에 시스템 전체(DB, 역직렬화, 계산 엔진, API 스펙, 세션/인증, 프론트엔드 UI, 배포 환경)에 미칠 수 있는 영향도를 사전에 파악하고 대책을 수립하기 위한 전사 표준 운영 절차(SOP)**입니다.

> ⚠️ **핵심 원칙**: 단 한 줄의 기능 코드를 변경하거나 신규 기능을 구현하더라도, **반드시 코드 작성 전에 본 문서(`docs/impact-analysis-guide.md`)를 조회(`view_file`)하여 사전 영향도 분석(Pre-Implementation Impact Analysis)을 완료**해야 합니다.

---

## 1. 사전 영향도 분석의 정의 및 의무화 프로세스

### 1.1 왜 기능 구현 '전'에 영향도를 분석해야 하는가?
- 기능 추가 후 발생하는 버그를 수습하는 '후속 조치' 방식은 이미 저장된 DB 데이터 파손, 프론트엔드 렌더링 다운, 세션 종료 등의 심각한 장애를 유발합니다.
- 사전 영향도 분석을 진행하면 **구버전 데이터 호환성(Fallback), 캐시 갱신 전략, API 파손 예방책을 코드 작성 단계부터 미리 설계**하여 장애 발생을 원천 차단할 수 있습니다.

### 1.2 전체 개발 워크플로우 (Sequence Flow)

```mermaid
flowchart TD
    A[1. 신규 기능 요구사항 접수] --> B[2. docs/impact-analysis-guide.md 참조]
    B --> C[3. 기능 구현 전 사전 영향도 분석 수행]
    C --> D[4. 하위 호환성 및 위험 예방책 설계]
    D --> E[5. 실제 기능 코드 및 테스트 구현]
    E --> F[6. 백엔드/프론트엔드 통합 검증]
    F --> G[7. 서브에이전트(Subagent) 교차 검수 수행]
```

1. **[요구사항 분석]**: 개발할 기능의 입력/출력/저장소/UI 영향 범위 정의.
2. **[사전 영향도 분석 수행]**: 본 가이드라인 7대 영역 체크리스트 및 사전 영향도 양식을 작성.
3. **[예방 전략 설계]**: 구버전 데이터 파싱 fallback, API 하위 호환성 유지 대책 수립.
4. **[구현 및 검증]**: 예방 전략이 포함된 상태로 개발 및 테스트 코드 실행 (`./gradlew test`, `npm run lint/build`).
5. **[서브에이전트 검수]**: 서브에이전트(Subagent)를 실행하여 사전 영향도 분석 결과와 구현체의 일치 여부를 교차 검증.

## 2. 사전 영향도 분석 7대 핵심 검토 영역 (Checklist)

신규 기능을 구현하기 전, 아래 7가지 영역에서 부작용이 발생할 가능성이 있는지 반드시 검토합니다.

### 1) DB 데이터 스키마 & 역직렬화 호환성 (Deserialization & Data Compatibility)
- **질문**: DB 컬럼, JSON Entity 필드(`WeatherSnapshot`, `OutfitRecommendation` 등)를 신규 추가하거나 변경하는가?
- **부작용 위험**: 기존에 저장된 DB JSON 데이터나 캐시에 새 필드가 없어 `null` 또는 기본값(`0`, `false`)으로 잘못 역직렬화될 수 있음.
- **사전 대책**:
  - 역직렬화 시 `null` 방지 기본값(Default value) 정의.
  - 구버전 데이터 감지 조건 수립 및 자동 캐시 갱신(`refreshIfMissing...`) 로직 사전 설계.
  - 필요 시 DB 마이그레이션 스크립트 준비.

### 2) 비즈니스 도메인 & 계산 엔진 영향 (Domain & Recommendation Engine)
- **질문**: 체감온도 보정, 기온 구간별 옷차림/준비물 룰 변경이 기존 계산 로직에 영향을 주는가?
- **부작용 위험**: 특정 기온 구간(예: 16℃ 일반 구간 vs 27℃/30℃+ 고온고습 구간)에서 의도치 않게 보정식이 중복 적용되거나 무효화될 수 있음.
- **사전 대책**:
  - 기온 구간별(30℃+, 27℃+, 20~22℃, 16℃ 이하) 보정 룰 우선순위 매트릭스 작성.
  - 단위 테스트(`RuleBasedRecommendationEngineTest` 등)에 기온별 분기 케이스 사전 추가.

### 3) API 계약 & 데이터 전송 스펙 (API Contract & DTO Boundaries)
- **질문**: Backend Response/Request DTO 수정이 Frontend 파싱 및 명세에 영향을 주는가?
- **부작용 위험**: 프론트엔드 컴포넌트에서 수정된 필드를 참조하지 못해 화면이 백화(Crash)되거나 타입 에러 발생.
- **사전 대책**:
  - `docs/api-spec.md` 명세 사전 업데이트.
  - 프론트엔드 타입(`App.tsx` 또는 `types.ts`) 동기화 확인.

### 4) 사용자 인증, 세션 & 보안 정책 (Auth, Session & Security)
- **질문**: 로그인, 세션 타임아웃, 쿠키, 권한 설정 변경이 기존 로그인 유지를 방해하는가?
- **부작용 위험**: 세션 쿠키 만료로 사용자가 접속할 때마다 재로그인을 해야 하거나, 서버/컨테이너 재시작 시 로그인 정보가 유실됨.
- **사전 대책**:
  - `SESSION_COOKIE_MAX_AGE` 등 쿠키 옵션 점검.
  - 컨테이너 재시작 시 세션 영속화를 위한 Spring Session JDBC 대책 고려.

### 5) 프론트엔드 UI/UX & 상태 관리 (Frontend UI State & Layout)
- **질문**: 탭 구조, 카드 레이아웃, 모바일 화면 반응형 순서 변경이 기존 사용자 흐름을 저해하는가?
- **부작용 위험**: 모바일 화면에서 스크롤 없이 핵심 추천 정보를 바로 보지 못하거나, 구버전 데이터 수신 시 렌더링 에러 발생.
- **사전 대책**:
  - React Optional Chaining (`data?.field ?? fallback`) 적용.
  - 모바일 반응형 뷰포트 사전 검수.

### 6) 외부 API 연동 & 배치/스케줄러 (External Services & Async Jobs)
- **질문**: 기상청 단기예보 API, 외부 푸시 서비스, 스케줄러 수정이 전체 흐름에 장애를 일으키는가?
- **부작용 위험**: 기상청 API 응답 값 누락 시 시스템 예외 발생.
- **사전 대책**:
  - 외부 파서(`KmaForecastParser`)에 안전한 default fallback 파싱 (`values.getOrDefault(...)`) 적용.

### 7) 배포 환경, Docker & 환경변수 (Deployment & Environment)
- **질문**: `.env` 또는 `docker-compose` 환경변수가 수정되거나 추가되었는가?
- **부작용 위험**: 배포 컨테이너에 환경변수가 전달되지 않아 런타임 오류 발생.
- **사전 대책**:
  - `.env.example`, `docker-compose.prod.yml`, 배포 런북 문서 동시 갱신.

## 3. 표준 사전 영향도 분석서 양식 (Pre-Implementation Impact Analysis Template)

신규 기능을 구현하기 전, 아래 양식을 활용해 사전 영향도 분석을 문서화하거나 서브에이전트 검수 시 전달합니다.

```markdown
### 📋 사전 영향도 분석서 (Pre-Implementation Impact Analysis)

1. **기능명 및 목적**: (예: KMA 습도 데이터 반영 및 습도 기반 체감온도 보정)
2. **수정/추가 예정 파일**: (예: RecommendationService.java, WeatherSnapshot.java, App.tsx 등)
3. **영향도 7대 영역 검토 결과**:
   - [DB/역직렬화]: 구버전 DB 저장본 역직렬화 시 `humidity` 필드 누락 발생 가능 -> `refreshIfMissing` 로직 설계 완료
   - [도메인 엔진]: 27℃ 이상 구간에만 고습 보정 적용, 16℃ 일반 구간은 미적용 분기 확인 완료
   - [API 계약]: RecommendationResponse DTO 습도 필드 추가 및 api-spec.md 업데이트 예정
   - [인증/세션]: 세션 영향 없음
   - [프론트 UI]: 요약 카드 및 탭 UI에 습도 카드 추가 예정
   - [외부 API]: KMA REH 파싱 기본값 50 설정 완료
   - [배포/환경]: 추가 환경변수 없음
4. **하위 호환 및 위험 차단 대책**: (기존 DB 데이터 호환성 유지 및 자동 캐시 갱신 로직 사전 수립)
```

## 4. [부록] 지난 사례를 통해 입증된 영향도 분석의 중요성 (Past Case Studies)

이 부록은 기능 구현 전 사전 영향도 분석을 소홀히 했을 때 어떤 문제가 발생하는지 보여주는 실제 사례 모음입니다.

### 사례 1: DB 역직렬화 파손 및 습도 0% 사건
- **상황**: 습도 기능 추가 시 DB에 기존 저장된 추천 데이터의 역직렬화 영향을 사전에 검토하지 않고 개발함.
- **결과**: 기존 DB 저장 데이터 조회 시 `humidity` 필드가 없어 기본값 `0`으로 파싱되어 `humidity: 0` 반환 및 체감온도 보정이 무효화되는 장애 발생.
- **사전 영향도 분석 적용 시**: 코드 개발 전 "기존 DB 저장본 역직렬화" 영향을 검토했다면 개발 단계부터 `refreshIfHumidityMissing` 자동 캐시 갱신 로직을 반영하여 장애를 방지할 수 있었음.

### 사례 2: 16℃ 기온 보정 조건과 도메인 엔진 조건식
- **상황**: 기온이 16℃일 때 습도 보정이 왜 안 되는지 문의 발생.
- **분석**: 도메인 엔진 상 습도 상승 보정은 27℃ 이상 고온 구간 조건식에만 작용하는 의도된 설계임. 사전 영향도 분석으로 기온 구간별 보정 범위를 미리 명시함으로써 혼선을 예방함.

## 5. 결론 및 행동 지침

1. **개발 개시 전**: 반드시 `docs/impact-analysis-guide.md` 문서를 먼저 읽고 사전 영향도 분석을 작성한다.
2. **개발 진행 중**: 사전 분석에서 수립한 하위 호환성/Fallback 대책을 반영하여 코드를 작성한다.
3. **개발 완료 후**: 서브에이전트(Subagent)를 호출하여 사전 영향도 분석서와 실제 구현 내용의 정합성을 최종 검수받는다.
